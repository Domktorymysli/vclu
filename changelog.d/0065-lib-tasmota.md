### Lua runtime

- **A Tasmota device is one line in a module** - `require("lib/tasmota")`: `tasmota.switch(topic, { relay = 2 })` is a `VirtualSwitch`, `tasmota.dimmer(topic)` a `VirtualDimmer` (Tasmota's Dimmer 0..100 on vCLU's 0..1), `tasmota.sensor(topic, "ENERGY.Power", { unit = "W" })` a read-only `VirtualNumber` from `tele/<topic>/SENSOR` (a write fails; `p:expose()` is read-only too, with `expose(p, ...)` pass `readonly = true`). The library keeps the state from `stat/<topic>/POWER<n>`, `RESULT` and `tele/<topic>/STATE`, sends a command once from Lua, a dashboard or Home Assistant, never sends a state from the device back, and asks for the state on start, when MQTT connects and when the device comes back (LWT `Online`). A press on the device is recorded in history with the device as the actor (`device:<topic>`). `tasmota.online(topic)` follows LWT, and `tasmota.devices()` lists what Tasmota's own discovery announced (nothing is created from it). `expose()` stays in the module; the device keeps Tasmota's default Full Topic (`%prefix%/%topic%/`); the module must not subscribe the library's `stat/<topic>/+` and `tele/<topic>/+` itself (MQTT keeps one callback per pattern). Used so far with a Sonoff Basic only (one relay, Tasmota 13.3.0), whose messages the tests replay; relays 2 and up, the dimmer and sensors follow Tasmota's documented messages but are untried on a device; colour lights, shutters and button events are not supported ([#65](https://github.com/Domktorymysli/vclu/issues/65)).

### MCP

- **`vclu_draft_test` delivers MQTT messages** - the step `{"mqtt": "stat/<topic>/POWER", "payload": "ON"}` hands a message to the subscriptions of every MQTT client as the broker would; what the module publishes shows in `blocked_calls`.
