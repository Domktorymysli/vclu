### Grenton

- **Object Manager project import** - the OM Files tab takes the project itself (`.omp`, or a project `.zip`) next to the diagnostic pack: it registers the same CLUs and objects as the pack built from it, the vCLU itself skipped. Projects from OM 1.3 to 1.8 are read; what vCLU cannot read is listed as a warning and the rest is imported. Names that are not letters, digits and `_`, Lua keywords, or taken by another object of the CLU are left out of the generated Lua (the object goes by its ID), also for om.lua from a diagnostic pack; a CLU whose name is a Lua keyword or one of the runtime's globals (`_`, `os`, `color`, ...) gets its objects under its ID in lower case instead of replacing that global. A proxy the Lua runtime refuses is reported as an error of the upload, no longer only in the log. Only the OM version is taken from `properties.xml`, which holds the project's keys; the upload is not kept on disk ([#178](https://github.com/Domktorymysli/vclu/issues/178)).

- **Importing a project again is safe** - the same project any number of times leaves the same files, and the dashboards made from it are not touched. A project is the whole house: CLUs it no longer has are removed as a delete would remove them, and the upload lists them; an import with errors removes nothing, and the vCLU's own file stays ([#178](https://github.com/Domktorymysli/vclu/issues/178)).

- **What an import changes, before it does** - choosing a file on the OM Files tab first shows what the import would change: CLUs removed, objects removed or of another type, a CLU renamed (its objects' table with it), and the lines of your Lua in `modules/` that work now and would name a missing object after it. Nothing is stored until you choose Import; an import that changes nothing of that goes ahead at once. After an import or a delete the answer lists the lines in `modules/` that name an object no CLU has (`brokenRefs`), by registry path (`"CLU….DOU0001"`) or through a CLU's table (`parter.light`), comments left out ([#178](https://github.com/Domktorymysli/vclu/issues/178)).

- **Deleting a CLU forgets what the project import wrote about it** - deleting an OM file removes the CLU's files in `ai/om/` and its row in `index.md`, which then says the CLU was deleted; deleting the last one removes `ai/om/` and the stored myGrenton interfaces. Dashboards made from them stay (they are the user's), and the Dashboards tab marks the widgets whose CLU is no longer imported ([#178](https://github.com/Domktorymysli/vclu/issues/178)).

### MCP

- **Event bindings and CLU scripts for the agent** - an import of a project, or of a diagnostic pack that carries one, writes `ai/om/`: `index.md`, one file per CLU with its objects, peripherals and event bindings (in OM's notation, `Home->light->SwitchOn(0)`), and the CLU's scripts in `<CLU>-scripts.md`. `index.md` tells the agent how OM's notation reads in vCLU's Lua (`_:get("CLU….DOU0001"):switchOn(0)`), with examples from the project, and lists the objects OM's bindings and scripts already command, so an automation does not fight them unseen. The next import replaces the directory; a diagnostic pack without a project removes it ([#178](https://github.com/Domktorymysli/vclu/issues/178)).
