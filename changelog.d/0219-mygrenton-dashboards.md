### Grenton

- **myGrenton interface from the project** - an import of the Object Manager project, or of a diagnostic pack that carries one, also reads the myGrenton interface designed in OM (`nodes/<id>/data.json`) and translates it into vclu's own model of dashboards, kept in `imports/mygrenton/`; a project or pack without one removes it, a single om.lua leaves it alone. Only the translator knows Grenton's format. Every value is checked: CLU and object IDs as in om.lua, scripts and user features as Lua names, indexes as numbers, a script's arguments as numbers and plain strings, and what a widget names is looked up in the project. A scheduler, a widget whose object is not in the project, a command to the CLU itself or a call that fails a check is left out with the reason ([#219](https://github.com/Domktorymysli/vclu/issues/219)).
- **Dashboards tab** - the Grenton page lists the pages of the imported interface with their widgets (what each reads and does) and what was left out; the chosen pages become plain dashboard code in `modules/dashboards/grenton/` (one `page_<id>.lua` each, joined as tabs), which is the user's from then on. vclu replaces a file it wrote only after asking, never one the user wrote or changed; it adds `require("dashboards/grenton")` to `modules/init.lua` only when asked, and then reloads Lua. Each page loads on its own, so one that fails does not stop the others ([#220](https://github.com/Domktorymysli/vclu/issues/220)).
- **`MyGrenton` helpers** - the reads and commands those files use: `MyGrenton.value`, `feature`, `variable`, `isOn`, `text`, `set`, `execute`, `script`, `onOff`, `load`. Reads never wait for a CLU: what the registry follows comes from it, the rest is asked in the background and the widget shows the last answer. Commands go to objects through their proxies. `CLU_REMOTE:getAsync(name, done)` reads a user feature without blocking ([#219](https://github.com/Domktorymysli/vclu/issues/219)).
