### Grenton

- **GATE Alarm objects** - an Object Manager import (diagnostic pack, the GATE's om.lua alone, or the project) registers a GATE Alarm's alarm objects under `<CLU ID>.<object ID>` with their names: Satel partitions, inputs, outputs and the panel connection (Grenton's SatelZone, SatelInput, SatelOutput, Satel; classes 100-103), and Jablotron sections, PG outputs, devices and the connection (classes 150-153). They are `RemoteGateSatelZone`, `RemoteGateSatelInput`, `RemoteGateSatelOutput`, `RemoteGateSatel`, `RemoteGateJablotronSection`, `RemoteGateJablotronOutput`, `RemoteGateJablotronDevice` and `RemoteGateJablotron` in Lua: Grenton's *zone* is Satel's partition and its *input* Satel's zone, while vCLU's own Satel integration (which talks to the panel's ETHM module itself) uses Satel's names (`SatelPartition`, `SatelZone`), so the GATE's objects carry `Gate` in their names and the two never mix. Their values follow the GATE on the Sync list, with the events Object Manager lists (`OnArm`/`OnDisarm`, `OnSwitchOn`/`OnSwitchOff`, `OnConnected`/`OnDisconnected`), told against the last known state, so a zone that is armed, then unknown (-1), then disarmed fires `OnDisarm`; `armZone()`, a section's `arm()`/`armPartially()` and the outputs' `switchOn()`/`switchOff()` go to the GATE; nothing else does: the connections (Satel, Jablotron) are read-only, no feature is written (they are the GATE's settings, e.g. `Nr`, which would repoint an object, or the panel's port and encryption), and `set(0, v)` on a zone, section or output is turned into those methods. A GATE Alarm is told by FwType 00000002 and HwType 00000012 in its om.lua; the same classes on any other CLU (an HTTP GATE has the same hardware) are left out with a warning in the upload's answer. The numbers come from Object Manager's definitions of the GATE Alarm and are not yet checked on one; unverified in particular: what a Jablotron section's State numbers mean (0 is taken as disarmed, any other as armed, so an alarm or exit-delay state may fire `OnArm`) ([#214](https://github.com/Domktorymysli/vclu/issues/214)).
- **Disarming a GATE Alarm needs `grenton.gateAlarm.allowDisarm`** - new setting in `.vclu.json`, default false, for every GATE Alarm, as the Satel integration's `allowDisarm`. Without it vCLU refuses a zone's DisarmZone and a section's Disarm, by the method, `execute(n)`, `set(0, 0)`, Wire, MCP or Home Assistant, and logs a warning (Home Assistant, HomeKit and the cloud get no error back): the guard is in `RemoteObject`'s `get`/`set`/`execute`, which every way in goes through, and it reads the setting from Go through a function taken when the runtime loads, so a script cannot replace it; the guard's tables (`SECRET`, `DISARM`, `METHODS`) are read-only from Lua, and the guard keeps its own copy of them and of each object's ID. Arming always works. The setting is one for all GATE Alarms and all their zones and sections, and a zone exposed with `expose()` is a switch in Home Assistant (and the cloud): with `allowDisarm` on, whoever can switch it there disarms it; `expose({ readonly = true })` only shows the state. Raw paths are out of reach of any guard: a script sent to the GATE (`clu:execute(0, "...")`) and a subscription asked by hand (`RemoteSubscription.subscribe(...)`) ([#214](https://github.com/Domktorymysli/vclu/issues/214)).
- **The panel's secrets stay out of vCLU** - the features that hold the panel's address, admin and user passwords, access codes and encryption key are never read or written through the proxies or Wire, and the copy of an om.lua vCLU keeps (`imports/om_<serial>.lua`) has no `:set` line of a GATE's objects and no Wi-Fi network or password of a GATE; copies kept before, or brought back by restoring an older backup, lose them at the next start or reload (only a count is logged) or when the proxies are regenerated. The agent's files about an imported project (`ai/om`) show a script's or binding's write into a GATE object's features, and any string on a line naming a password or code feature, as `"(removed by vclu)"`. Zones and sections reach Home Assistant and HomeKit only by `expose()` (a switch: on arms, off disarms when allowed); inputs and devices are exposed as binary sensors and outputs as switches, read-only in HomeKit as the Satel integration's. A zone whose state is unknown (-1) is shown as unknown, not disarmed: `None` (unknown) in Home Assistant, "No Response" in HomeKit and no `on` in the cloud's states; the same holds for any switch or binary sensor reporting a negative value ([#214](https://github.com/Domktorymysli/vclu/issues/214)).
