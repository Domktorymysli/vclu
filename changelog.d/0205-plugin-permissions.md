### Plugins

- **Plugin API versions** - `"api"` in `plugin.json` names the contract a plugin is written for. A plugin without it is on API 1 and runs as before: `lan`, `mqtt` and `modbus` without declaring them, events and expose paths with any name, the `HTTP`, `HttpClient` and `MQTT` globals (read-only). A plugin for a newer API than this vclu runs does not load and says to update vclu; `Plugin.apiVersion` is 2. `"strict": true` in the `plugins` section of `.vclu.json` loads only API 2 or later ([#205](https://github.com/Domktorymysli/vclu/issues/205)).
- **Plugin API 2: permissions** - `plugin.json` declares what a plugin reaches, each permission with its parameters and, for a wide one, why: `"permissions": {"internet": {"hosts": ["api.example.com"]}, "lan": {"ports": [80]}, "mqtt": {"subscribe": ["shelly/#"], "publish": ["shelly/+/set"]}, "modbus": true}`. `lan` allows HTTP and WebSocket to local addresses (checked after DNS resolution) on its ports, by IP address or by a house name (one label such as `shelly-1a2b`, or under `.local`, `.lan`, `.home`, `.home.arpa`, `.internal`, `.localdomain`); another name needs the internet host list, or on any port with `"why"`; `mqtt` the plugin's MQTT methods on its topic filters, or any topic with `"why"`; `modbus` the `Modbus` table, to a gateway by its IP address or a house name. `"why"` (a text or `{"pl", "en"}`) goes into the install dialog. `"permissions": {}` asks for none; an API 2 plugin without the field does not load. The official plugins are on API 2.
- **A plugin for a newer vclu says so** - a permission, a permission's field, an action's field or a form field type this vclu does not know refuses the plugin at download and at load with "needs a newer vclu", instead of running it with less; `"requires": {"vclu": ">=1.13.0"}` is checked the same way. `plugin:has(name)` tells a plugin what this vclu offers (a method, `"permission:udp.broadcast"`, `"form:host"`). An unknown top-level key is logged; an author's own starts with `x-`. On plugin API 2 a plugin calls `plugin:httpRequest`; `plugin:httpGet` and `plugin:httpPost` stay for plugin API 1.
- **Actions in plugin.json** - a plugin declares the actions voice assistants and agents call (`"actions": [{"name", "description", "params", "confirm"}]`) and gives each its function with `plugin:action(name, fn)`; the install dialog lists them and an update adding one waits for the user. An action marked `"confirm": true` runs only when the caller says the user agreed (`?confirmed=true` over HTTP, 409 without it; `confirmed: true` in `vclu_app_action`), and plugin code cannot turn that off.
- **A plugin's KV store has limits** - a key up to 128 characters, a value up to 256 KiB, the whole store up to 1 MiB; `secure` keeps a value out of the logs, it does not encrypt the file.
- **Plugin API 2: internet hosts** - `"internet": {"hosts": [...]}` in `permissions` lists the servers an API 2 plugin connects to: `["api.example.com", "*.example.com"]` (`*.example.com` is the subdomains, not `example.com`), an exact IP address, or `["*"]` for any server, with `"why"`. Without it an API 2 plugin reaches no internet host; API 1 is unchanged. The host name in the URL is checked, also after every redirect; a refusal says `api.example.com is not on the host list of @x/foo (permissions.internet)`. The LAN boundary is separate: a listed name that resolves to a local address still needs `lan`. The plugins page shows the hosts ("connects to: …"), and `"*"` with a warning; an update adding a host or switching to `"*"` waits for the user, the hosts allowed before keep working. A manifest with a malformed host (a scheme, path or port) is refused.
- **What a plugin asks for and what it gets** - the user's grants are kept on the installed plugin in `.vclu.json` (`grants`). Installing allows what the confirmation showed (hosts and ports in the downloaded files that it did not show wait); a plugin installed earlier keeps what its files ask for now. An update that asks for more runs without it until the user allows it: the log says so, `GET /api/plugins/installed` lists it in `pendingPermissions`, `POST /api/plugins/:id/permissions` allows it; the plugins page shows it with an "Allow" button.
- **Permissions narrowed to hosts and topics** - in the plugin's permissions on the plugins page the user can limit `lan` to some hosts (IP addresses or prefixes) and `mqtt` to topic filters for subscribing and publishing: `"grants": {"lan": {"hosts": ["192.168.1.20"]}, "mqtt": {"subscribe": ["shelly/#"], "publish": []}}`. No list allows any host or topic, an empty list none. A request to another local address or a subscription outside the filters is refused with a message that names the plugin's settings. The `HTTP`, `HttpClient` and `MQTT` globals of plugin API 1 cannot be limited, so such a plugin has them only while `lan` or `mqtt` is allowed in full. The permissions API refuses keys it does not know.
- **A repository can be one plugin** - a repository with `plugin.json` at its root and no `plugins.json` is added like any other; its namespace is the manifest id's (`@jan/foo`) or the repository owner's.
- **A stricter sandbox** - on every plugin API, a plugin gets its own copies of `string`, `table` and `math`; `Logger`, `JSON` and `Plugin` cannot be modified. On API 2 the `HTTP`, `HttpClient` and `MQTT` globals are gone (use `plugin:httpRequest`, `plugin:mqttSubscribe`). Objects a plugin did not create, other plugins included, are read-only also through `pairs`: only `get`, `getX`, `isX` and `hasX` methods can be called on them, and another plugin shows only its sensors and controls. `Plugin.getPlugin` returns the plugin's own instance; its id cannot be changed. Event payloads reach a plugin read-only, a plugin clears only its own timers, and a disabled plugin's pollers, HTTP retries and exposed objects go away with it. On API 2 an `expose` path goes under the plugin's id, and events a plugin emits start with its prefix: an official plugin's short id or its first word (`sun:`), any other plugin's full id (`@jan/foo:changed`). `Plugin.getPlugin` by short id prefers the `@vclu` plugin and refuses an ambiguous name. No official plugin is affected.
- **Read-only data in the standard library** - an event payload or a registry object a plugin reads works as before with `JSON:encode`, `plugin:encodeJson`, `table.concat` and `unpack`, and is passed on whole by `plugin:emit` and `plugin:mqttPublish`; `table.insert`, `table.remove` and `table.sort` on it are refused.
- **Contract change: plugin ids are lower case** - a namespace and a short id use `a-z`, digits, `.`, `_` and `-`, without `--` or a `-` at either end, so two ids never share a directory or KV file. An exposed path of a plugin that would share an MQTT topic with another path is refused; a plugin cannot change an object a module exposed. A plugin without `lan` is also refused this machine's own networks, global IPv6 included.
- **Reading a CLU needs `clu`** - on plugin API 2, plugin code that would send a request to a CLU (a feature read by index on a Grenton object, a `CLU_REMOTE` read) is refused without `clu`; what vclu already knows of the object (`getValue` and other reads from its state) stays readable. An API 1 plugin keeps it, with a warning in the log. Module code is not affected.
- **Objects a plugin did not create show no `_` fields** - their internal state (`_name` fields) is not readable or listed by `pairs`; their read methods still work.
- **Remote access of a plugin's device is the user's** - on plugin API 2, `:remote()`, `:roles()`, `:pin()` and `:confirm()` on a handle a plugin exposed are refused in plugin code: the user's module calls them, on the handle from `Plugin.getPlugin(id):getExposed()` or on its own `expose` of the plugin's object. API 1 is unchanged.
- **A Grenton object's index is an integer** - `get`, `set` and `execute` on a CLU object refuse an index that is not one, instead of building it into the code sent to the CLU.
- **An update records its repository** - an installed plugin from before repositories were recorded gets the one it is updated from; from then on only that repository updates it.
- **`plugin:mqttPublish` works** - it passed `retain` and `qos` in the wrong order and failed on every call.
- **Updates only from the plugin's repository** - another repository listing the same id is not an update: the bell does not offer it and installing from there is refused until the plugin is uninstalled. The installed plugin records the repository's address (`repositoryUrl`): a repository added again under the same name at another address does not update it, and the plugins page shows "source moved"; the same address written with a trailing `/` or `.git` is the same repository. A repository without a namespace gets its name in lower case as the namespace (Polish letters without accents). A version downloaded from one repository is not reused for another one with the same id and tag.
- **Safer updates** - a version that needs a newer plugin API than this vclu is refused at download and the installed one keeps running; so is a version on a lower plugin API than the installed one (recorded as `api`): the install dialog says so, and the plugin can be uninstalled and installed again on it. Files replaced by hand with a lower API do not load; a plugin waiting for permissions shows in the notification bell until they are allowed or the plugin is disabled. An installed plugin whose id is not lower case is reported at load with how to fix it.
- **Permissions only from a readable configuration** - when `.vclu.json` cannot be read, plugins do not load and nothing is installed or downloaded, instead of a plugin getting what its `plugin.json` asks for. A host written as a number is refused unless listed.
- **API 1 shown as it is** - the install dialog and the plugin card show a plugin on API 1 as reaching any internet server, with a note that it runs outside the permissions.
- **Installs as confirmed** - installing or updating needs what the confirmation showed and the user accepted (`accept` and `seen` from the preview, also with an API key); installing takes the plugin API the confirmation showed and refuses other files ("open the installation again"); installs run one at a time, and a reload fetches files under the same lock. A repository address keeps its path's case except on GitHub. The plugins page offers an update only when installing it would go through.
- **Repositories kept at arm's length** - a plugin file over 4 MiB, a manifest listing more than 64 files or a plugin API below 1 refuses the download and leaves nothing behind; a repository's `plugin.json` and documentation are read up to 1 MiB, and the documentation is shown as text and plain formatting only. A plugin removed from `.vclu.json` does not load, and an entry without grants whose files had to be fetched again waits for the user. An update of a `lan`, `udp` or `tcp` grant from before ports were recorded keeps the ports of the files it replaces.
- **Before you update** - the first load after the update records in each plugin's grant the ports and actions its `plugin.json` on disk declares (older grants had no ports or actions); from then on a new host, port, topic or action in a plugin update waits for "Allow". Manifest keys are exact: a key in another case, written twice or unknown refuses the plugin with "needs a newer vclu". `requires.vclu` is `>=X.Y.Z`; a pre-release such as 1.13.0-rc counts as 1.13.0.
