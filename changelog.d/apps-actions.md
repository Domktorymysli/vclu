### Plugins

- **A plugin can be a small app: its own dashboard and named actions** - `plugin:dashboard(id)` gives the builder of `Dashboard.new` for a dashboard at `/d/<shortId>_<id>` (`-` in the short id as `_`), behind login unless the plugin sets another auth. Its widget callbacks run as the plugin's code, errors go to the plugin's log; widgets that reach the house by name (`area`, `floor`, `room`, `covers`, `calendar`, `schedule`, `chart`, `bars`) are not available, and the app is not served the house's cameras through it, and an id a module or another plugin already uses is refused. `plugin:action(name, fn)` gives an action declared in `plugin.json` the function agents and voice assistants call: params are typed (`string`, `number`, `boolean`), unknown ones refused, text up to 1000 characters; at most 32 per plugin. Both go when the plugin is disabled, reloaded or uninstalled (uninstalling now also stops a running plugin). The dashboards page marks a plugin's dashboard. No permission needed.
- **Who opens a plugin's dashboard is the user's** - a plugin declares its dashboards in `plugin.json` (`"dashboards": [{"id", "name", "description"}]`) and on plugin API 2 builds only those. It can keep one behind login or a PIN, never open it to everyone, give it a PIN code or put it in the vclu app. A module grants that: `Plugin.getPlugin("@vclu/zakupy"):dashboardAccess("lista", {name, auth = "session"|"pin"|"public"|"off", pin, remote = {pin, roles}})`, applied at once and whenever the plugin builds the dashboard again; "off" takes it off the panel. The plugin wizard has a Dashboards step for it (who can open it, the app, a PIN there, roles from the cloud as chips) and writes the call into the plugin's module after showing the diff.

### HTTP API

- **Plugin actions** - `GET /api/plugins/actions` (`?plugin=` for one) lists `{plugin, name, description, params}`; `POST /api/plugins/:id/actions/:name` with the params as a JSON body answers `{result}`, or `{error}` with 404 (no such action, or not allowed yet), 400 (params), 409 (it asks for confirmation: `?confirmed=true` once the user agreed) or 422 (the action failed). The list has `confirm: true` for those. Same auth as the other plugin routes; the action runs as the caller.

### MCP

- **`vclu_app_actions` and `vclu_app_action`** - list and run the actions of installed apps (control layer, like `vclu_device_set`): a bot sees a plugin's actions when its profiles read the plugin id and runs them when they control it. `vclu_runtime_schema` lists each running plugin's actions and the `apps` API.
