# 0002: Libraries shipped with the runtime

- **Status:** proposed
- **Date:** 2026-10-18

## Context

The Lua runtime has two layers. The core (`pkg/lua/runtime/core`, `objects`, `grenton`,
`integrations`) is loaded by the bootstrap into every Lua state and is a contract: user modules
and agents depend on every public function in it, so it stays small (`pkg/lua/AGENTS.md`).
User modules (`modules/` on an installation) are written by the user or an agent.

Some code fits neither. The Smart Panel library (#44) turns button events into pages, menus and
frames: it is a ready-made policy built only from core functions (`RemotePanel`, timers,
`onChange`). It is too large and too opinionated for the core, and too general to be copied
into every installation's modules. Recipes like it (a thermostat with hysteresis, a lighting
scene builder) will follow, so they need one place and one way to be required.

## Decision

- **Location.** A library shipped with vCLU is one file in `pkg/lua/runtime/lib/<name>.lua`
  (a larger one may become `lib/<name>/init.lua`). It is installed with the runtime
  (`/opt/vclu/runtime/lib/` on a server, inside the release archive and the Docker image).
- **Loading.** The bootstrap never loads a library. A module asks for it:
  `local Panel = require("lib/panel")`. A library returns its table and sets no globals, except
  an entry point a CLU calls by name, which belongs in the core (`click` lives in
  `RemotePanel`, not in `lib/panel`).
- **Dependencies.** A library uses only the public core API and other libraries. The core
  never requires a library.
- **Contract.** Public functions carry `@api public` and appear in
  `docs/ai/lua-api-reference.md` (generated by `tools/generate-api-reference`). Changing a
  public signature needs a `Contract change:` note in its changelog entry (`changelog.d/`), as for the core.
- **Tests.** A library has its tests in `pkg/lua/<name>_test.go` on a virtual clock, and works in
  `vclu_draft_test`, so an agent can check a module that uses it before promoting.
- **Shadowing.** `modules/` comes before the runtime on `package.path`, so a user file
  `modules/lib/panel.lua` replaces the shipped library. That is allowed (a user can try a fix),
  but agents must not create such a file by accident: the MCP instructions say libraries are
  required, not copied.

## Consequences

- The core stays small; policies can grow and change in libraries with their own tests.
- A user updates a library by updating vCLU; a module pinned to an old behaviour has to copy the
  file into `modules/lib/` and own it.
- `lib/panel` is the first library. `vclu_runtime_schema` and `docs/ai/examples.md` describe it
  for agents.

## Alternatives considered

- **Load libraries in the bootstrap as globals** (`Panel` always present): every Lua state pays
  for code most installations never use, and every global becomes core contract.
- **Plugins** (`plugins/<name>/`): plugins connect vCLU to an outside service and have a
  manifest and configuration; a pure Lua library has neither, and plugins are not meant to be
  required by other modules.
- **Copy into `modules/` on install**: the user's directory would mix their code with shipped
  code, and updates would overwrite or miss user changes.
