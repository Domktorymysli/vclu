## Goal
After an Object Manager import (diagnostic pack or project), the Satel objects of a GATE Alarm are
in vclu like the other objects of the house: in the registry under the GATE's CLU ID, readable and
usable from Lua and dashboards, with their events, and commands go to the GATE. Both upload paths
read them: a diagnostic pack (`CLU*/om.lua` of the GATE) and a single om.lua file
(`handle_web_om.go`, both go through `omparser.Parse`).

## Context
- A GATE Alarm (`FwType 00000002`, `HwType 00000012`) declares its objects in om.lua as GATE
  objects, without a module:
  ```lua
  SAT0001 = GATE:new(100, "SAT0001")
  -- NAME_PERIPHERY alarm_ground=SAT0001
  ```
  `pkg/omparser` reads peripherals only as `THE… = OBJECT:new(...)` (`rePeripheryObject`), so these
  lines are skipped today and the objects never reach vclu.
- The same om.lua sets their features with `SAT0001:set(n, ...)`: the panel's IP, `AdminPassword`,
  `EncryptionKey`, the users' `UserPassword`. vclu needs none of them and must not read, store or log
  them.
- The objects as vclu presents them (the class is the first argument of `GATE:new`):

  | Class | Type | Value (feature 0) | Methods (execute) | Events |
  |---|---|---|---|---|
  | 100 | SatelZone | 1 armed, 0 disarmed, -1 unknown (no connection) | 0 ArmZone, 1 DisarmZone | 0 OnChange, 1 OnArm, 2 OnDisarm |
  | 101 | SatelInput | 0 Normal, 1 Violated | — | 0 OnChange, 1 OnSwitchOn, 2 OnSwitchOff |
  | 102 | SatelOutput | 0 Off, 1 On | 0 SwitchOn, 1 SwitchOff | 0 OnChange, 1 OnSwitchOn, 2 OnSwitchOff |
  | 103 | Satel | 0 Disconnected, 1 Connected | — (only setters of its settings) | 0 OnConnected, 1 OnDisconnected, 2 OnError |

  The table is a summary: check the method and event numbers against a GATE Alarm connected to a
  panel when implementing (what it sends and what it accepts).
- Names differ between Grenton and Satel: Grenton's *zone* (SatelZone) is Satel's *partition*
  (`strefa`), and Grenton's *input* is Satel's *zone*. vclu's own Satel integration (`pkg/satel`,
  `pkg/lua/runtime/integrations/satel/`) uses Satel's names (`SatelPartition`, `SatelZone`). Use
  separate names for the GATE objects so the two never mix.
- That integration talks to the panel's ETHM module itself. This ticket is for houses where the GATE
  Alarm already owns the connection to the panel; it does not replace or change `pkg/satel`.
- Disarming is the sensitive command. `pkg/satel` refuses `Disarm` unless `AllowDisarm` is set
  (`panel.go`, `TestPanelDisarmAllowed`); the GATE objects follow the same rule: ArmZone works,
  DisarmZone only when the configuration allows it.
- Other CLUs' objects are proxies (`pkg/lua/runtime/objects/Remote*.lua`, generated by
  `omparser.GenerateProxy`), with states from `grenton/protocol/RemoteSubscription.lua`.
- #178 (import of the project file) writes the GATE's peripherals into om.lua as GATE objects, as
  Object Manager does (`pkg/omproject/omlua.go`), so once it is merged a project import gets these
  objects through the same parser; nothing extra is needed for it here.

## Files
- `pkg/omparser/parser.go`, `types.go`, `generator.go`
- `pkg/lua/runtime/objects/` (proxies for the GATE objects)
- `pkg/lua/runtime/core/ExposedObjects.lua` (if inputs and outputs are exposed)
- `pkg/config` (the setting that allows disarming)

## Acceptance criteria
- [ ] `omparser.Parse` reads `ID = GATE:new(100|101|102|103, "ID")` with its `NAME_PERIPHERY`; a test
      with om.lua lines as Object Manager writes them (anonymised).
- [ ] Uploading a diagnostic pack and uploading the GATE's om.lua alone give the same objects; a test
      for each in `pkg/web`.
- [ ] No value of a `:set(...)` line of these objects reaches the parsed result, the proxy files or the
      log: a test with a marker password checks the files in `imports/`.
- [ ] The proxies register SatelInput, SatelOutput and SatelZone under `<CLU ID>.<object ID>` with their
      names; their Value follows the GATE (remote subscription) and their events fire in Lua.
- [ ] SatelOutput `SwitchOn`/`SwitchOff` and SatelZone `ArmZone` are sent to the GATE; `DisarmZone` is
      refused unless the configuration allows it, tested both ways.
- [ ] A zone is not exposed to Home Assistant or HomeKit automatically (like a thermostat, only by
      `expose()`); inputs and outputs are exposed like other binary sensors and switches, or the PR says why not.
- [ ] Docs on docs.vclu.pl say what a GATE Alarm gives vclu and how it differs from the Satel integration.
- [ ] `go test ./...` and `go test -race ./...` pass.
- [ ] A changelog entry in `changelog.d/0214-gate-alarm.md`.

## Contract impact
New objects in the registry; none existing changes. The disarm setting is new configuration.
